## 本轮实现

### 并发和控制

Agent 使用独立有界通道：读取 8、文件写操作 2、文件传输 2、终端执行/输入 4、终端状态/取消控制 2。Gateway 在领取任务前按类别筛选，活跃任务由独立心跳续租；一个传输任务不再阻止下次普通读取的 poll。

不同任务仍有资源约束：相同操作 ID 去重，同终端输入协调，规范路径相同或相互包含的工作区写入协调。Gateway 文件接收全局 4、每设备 2，相同传输 ID 独立互斥。短配额临界区预留完整逻辑大小，不再将网络传输时间包在全局 Mutex 内。

这次进一步将 `terminal_read`、`terminal_cancel` 从输入通道中独立出来。PTY 输入只持有该终端 writer 的锁，并在阻塞线程写入，不再持有所有终端共用的 live-map 锁。取消不需要获取正在阻塞的输入锁。真实测试先构造不消费 stdin 的 PTY，再填充输入并同时读取/取消，而不是只测试一个空闲终端。

已完成的修改操作回执在取得执行容量之前读取，不让幂等重放排在长任务后面。阻塞文件编辑的资源 guard 被移动到实际执行写入的闭包内，外层 Future 取消不会过早释放它。

### 上传不再全程锁住工作区

入站文件在同目录临时文件中传输、校验；网络阶段不持有工作区发布锁。最后才取得写入资源锁，并在实际原子发布时重新检查目标版本。版本冲突不静默覆盖并发编辑。同目录暂存仍可能产生目录和临时文件，不宣称网络阶段零文件系统变化。

### 传输进度

`operation_get` 可返回阶段、`bytes_done`、`total_bytes`、`elapsed_ms`、`average_bps`、`instantaneous_bps`、`resumed_bytes`、`retry_count`、进度来源和新鲜度。

Agent 活跃任务每约 2 秒通过心跳携带有界进度快照，空闲时不额外发送进度心跳；Gateway 按设备、任务和会话校验。网关接收端直接记录实际写入 staging 的字节数，避免把发送端读取文件或交给 socket 缓冲的字节冒充对端已收到的内容。进度采样不需要模型逐次调用工具。

计数不等于文件最终校验/发布完成；阶段仍需要依次显示传输、校验、发布和完成。`progress_stale` 明确表示最近一次进度报告是否过期。进度是诊断信息，持久化完成回执才是操作结果。瞬时速率在停止前进或非传输阶段归零。

### 入站文件的在线 Range 恢复

新增 `resumable.rs`：网络中断后，在同一存活操作中保留已收到的 offset 和 SHA-256 状态，以 Range 请求继续。只有强 ETag 或调用方预期 SHA-256 可确认源身份时才组合多个响应；缺少身份时重新开始，不拼接来源不确定的数据。

每次验证 Content-Range 起止、长度和总大小。Range 被忽略或 If-Range 失配而返回 200 时，先截断临时文件并重置哈希，再消费完整响应。源 ETag/长度变化、偏移错误、压缩内容或最终 SHA 不符时拒绝发布。

每 4 MiB 对已写临时数据执行 sync_data，网络重试前同步，最终仍 sync_all 并校验哈希。最多六次内部网络重试并有退避。**这些同步点不是跨进程恢复检查点：尚未持久化完整恢复/发布状态机，进程重启不能续传。**

### 正确区分连接超时与无进展超时

去掉传输的固定 180 秒总期限。GET 连接/DNS 有界，接收使用 60 秒 idle 检测；请求持续有数据时允许总时长超过 idle 窗口。

reqwest 的 read_timeout 也在等待响应头时运行，不能直接用于完整上传。新增 `transfer_watch.rs`，同时观察上传 body 的需求变化和经过设备鉴权的网关接收计数；只有两边都不前进才判定上传 idle。发送端需求仅供超时判断，不直接作为用户可见接收进度。新增内部 `/device/file-progress/{id}`，不增加 MCP 工具数量，不返回凭据或文件正文。

设备到 Gateway 的导出目前仍是完整 POST 的最多三次发送重试，**尚不支持从网关已确认 offset 补传**。新 idle 监测不能被称作导出断点续传。

## 原生工具体验

本轮确实调用过新 `file_upload` 上传一个源码文件，线上返回 `file source lookup failed`，目标文件没有通过该次调用写入。之后使用版本校验的代码编辑完成实现。这个结果只证明这次文件源交接失败，不能据此断定唯一根因或宣布原生附件传输已修复。

本轮没有人为限速生产网络，也没有测出整个网页的加速倍数。测试使用本机临时目录、合成设备和凭据、本地 HTTP/真实子进程，不等于 NAS/公网/ChatGPT 原生附件验收。

## 发布与仍待完成

新 Gateway 应先升级，再升级 Agent；新 Agent 显式要求 dispatch_protocol=2，不会向旧 Gateway 静默使用新调度协议。原 0.2.0 Agent 不传新的 lane/progress 字段仍可连接新 Gateway。升级脚本和历史验收脚本里的固定版本断言需要随发布更新，不能直接将 0.2.0 的验收 JSON 用于 0.3.0。

本轮范围外或尚未解决：完整双向/跨进程断点续传、链接重新授权后的恢复、独立文件传输取消、严格工作区调度公平性、工作上下文接口、短命令一次性结果返回、终端硬性阻塞线程回收、完整发布自动化、跨平台/公网压力验收。64 MiB 文件上限保留。

其中终端取消保证与现有 Unix 进程组一致，不保证回收刻意脱离进程组的后代；输入阻塞被移出全局锁，但没有声称所有阻塞线程都能被强制中断。Progress 也不替代网络确认或持久检查点。

最终交付为已验证的 0.3.0 候选源码及证据；本轮没有构建新的 release 二进制，也没有部署 0.3.0。两台在线 Agent 最后仍报告 0.2.0。本报告是工程交接，不是安全认证、全平台验收或生产发布证明。
